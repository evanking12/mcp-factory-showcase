## Item 1 — `print()` → `logger.debug()` in worker + discovery {#item-1}

### Files changed

- `api/infra/worker.py` (2 substitutions)
- `api/services/discovery.py` (13 substitutions)

### Why

Both files contained `print(f"[DIAG {job_id}]...", flush=True)` calls that were
left over from early diagnostic instrumentation. In production these bypass the
Python `logging` system entirely, meaning they go straight to stdout with no
level filtering, no structured formatting, and no way to suppress them without
changing the code. The logging system already has a handler attached; the prints
were redundant noise.

### What changed

**`api/infra/worker.py`** — two calls in `_run_discovery`:

```python
# BEFORE
print(f"[DIAG {job_id}] entering _run_discovery", flush=True)
# ...
print(f"[DIAG {job_id}] _run_discovery returned {len(...)} invocables", flush=True)

# AFTER
logger.debug("[%s] entering _run_discovery", job_id)
# ...
logger.debug("[%s] _run_discovery returned %d invocables", job_id, len(...))
```

**`api/services/discovery.py`** — thirteen calls across the bridge pre-check,
bridge health probe, bridge blob-cache hit, per-attempt bridge failure, bridge
exhaustion, discovery cache hit, subprocess start/done, artifact upload
start/done, and final bridge-call status. All converted to `logger.debug()` with
`%s`/`%d` format parameters (not f-strings, per Python logging best practice to
avoid string interpolation when the message is never emitted at low log levels).

One additional fix in `discovery.py`: a `logger.warning()` call that was already
using an f-string for a blob-upload failure was converted to use `%s` positional
parameters for consistency.

### How to verify it worked

Set `PYTHONUNBUFFERED=1` and run the API with `LOG_LEVEL=DEBUG` (or set
`logging.basicConfig(level=logging.DEBUG)` temporarily). You should see
`[job_id] entering _run_discovery` etc. in the structured log stream, not raw
stdout.

### Rollback

The original calls were `print(f"[DIAG {job_id}] ...", flush=True)`. Replacing
the `logger.debug` lines back with equivalent `print` calls restores the old
behavior exactly. No logic changed — only the output channel.

## Item 2 — Consolidate four `_append_*` functions in storage.py {#item-2}

### Files changed

- `api/infra/storage.py`

### Why

`storage.py` contained four functions with an identical read-modify-write
structure:

```
read JSON list from blob → extend list → write back → log warning on failure
```

The four functions were:

- `_append_diagnosis_raw(job_id, record)` — writes to `diagnosis_raw.json`
- `_append_executor_trace(job_id, entries)` — writes to `executor_trace.json`
- `_append_explore_probe_log(job_id, entries)` — writes to `explore_probe_log.json`

(A fourth function `_append_transcript` was reviewed but **not changed** because
it uses a different format — plain text lines, not a JSON list — so consolidation
would have changed its semantics.)

Each of the three JSON-list functions was ~20 lines. They had diverged slightly
in their docstrings and local variable names but were functionally identical.
Any bug in the read-modify-write logic (e.g., an encoding error, a missing
null-check on the existing blob) would have to be fixed in three places.

### What changed

A new generic helper was inserted at line 124 of `storage.py`:

```python
def _append_json_list(job_id: str, blob_name: str, entries: list) -> None:
    """Generic read-modify-write helper: append *entries* to a JSON-list blob."""
    if not entries:
        return
    try:
        full_blob = f"{job_id}/{blob_name}"
        try:
            existing = json.loads(
                _download_blob(ARTIFACT_CONTAINER, full_blob).decode("utf-8", errors="replace")
            )
            if not isinstance(existing, list):
                existing = []
        except Exception:
            existing = []
        existing.extend(entries)
        _upload_to_blob(
            ARTIFACT_CONTAINER, full_blob,
            json.dumps(existing, indent=2, default=str).encode("utf-8")
        )
    except Exception as exc:
        logger.warning("[%s] _append_json_list(%s) failed: %s", job_id, blob_name, exc)
```

The three JSON-list functions were then replaced with thin one-line delegates:

```python
def _append_diagnosis_raw(job_id: str, record: dict) -> None:
    _append_json_list(job_id, "diagnosis_raw.json", [record])

def _append_executor_trace(job_id: str, entries: list) -> None:
    _append_json_list(job_id, "executor_trace.json", entries)

def _append_explore_probe_log(job_id: str, entries: list) -> None:
    _append_json_list(job_id, "explore_probe_log.json", entries)
```

**Public signatures are unchanged.** All call sites in the codebase continue to
call these three functions exactly as before. No call sites were modified.

### Behavioral differences to watch for

- **Error message format changed.** The old per-function `logger.warning` calls
  had messages like `[job_id] _append_diagnosis_raw failed: ...`. The new helper
  emits `[job_id] _append_json_list(diagnosis_raw.json) failed: ...`. If you are
  grepping logs for the old function names in warning messages, update the grep.

- **`_append_transcript` was NOT touched.** It still has its own full
  implementation writing plain-text lines, not JSON. Do not refactor it into
  `_append_json_list` without changing the transcript format too.

### Rollback

Restore the three original function bodies from git. The `_append_json_list`
helper can be left in place (it is harmless) or removed. The public API of
`_append_diagnosis_raw`, `_append_executor_trace`, and
`_append_explore_probe_log` is identical either way.

## Item 3 — Extract inline HTML/CSS/JS from `ui/main.py` {#item-3}

### Files changed

- `ui/main.py` — **major surgery**: removed a 4,018-line `_HTML` string literal
- `ui/static/app.css` — **new file**: 947 lines of extracted CSS
- `ui/static/app.js` — **new file**: 2,228 lines of extracted JavaScript
- `ui/templates/index.html` — **new file**: 843-line HTML template
- `ui/requirements.txt` — added `jinja2>=3.1.0` and `aiofiles>=23.0.0`

### Why

`ui/main.py` contained a single `_HTML = r"""..."""` string spanning roughly
lines 174–4193 of the original 4,488-line file. That string embedded:

- ~948 lines of CSS inside a `<style>` block
- ~830 lines of HTML body markup
- ~2,228 lines of JavaScript inside a `<script>` block

This meant the entire SPA lived in a Python string with no syntax highlighting,
no linting, no hot-reload support, and IDE navigation that was completely blind
to the frontend code. The `@app.get("/")` endpoint just returned
`HTMLResponse(_HTML)` with no way to template or parameterise anything.

### Exact extraction boundaries (from the original file, 1-based line numbers)

| Content                                 | Original lines |
| --------------------------------------- | -------------- |
| `_HTML = r"""<!DOCTYPE html>`           | 174            |
| `<html>`, `<head>`, `<meta>`, `<title>` | 175–179        |
| `<style>` open tag                      | 180            |
| CSS content                             | 181–1127       |
| `</style>`                              | 1128           |
| CDN mermaid `<script>`                  | 1129           |
| `</head>`                               | 1130           |
| `<body>` and HTML body markup           | 1131–1960      |
| `<script>` open tag                     | 1961           |
| JavaScript content                      | 1962–4189      |
| `</script></body></html>"""`            | 4190–4193      |

### What changed in `ui/main.py`

1. Added two imports:

   ```python
   from fastapi.staticfiles import StaticFiles
   from fastapi.templating import Jinja2Templates
   ```

2. After the app and middleware setup, added:

   ```python
   _UI_DIR = Path(__file__).resolve().parent
   app.mount("/static", StaticFiles(directory=_UI_DIR / "static"), name="static")
   templates = Jinja2Templates(directory=_UI_DIR / "templates")
   ```

3. The `@app.get("/")` endpoint changed from:

   ```python
   @app.get("/", response_class=HTMLResponse)
   async def root() -> HTMLResponse:
       return HTMLResponse(_HTML)
   ```

   to:

   ```python
   @app.get("/", response_class=HTMLResponse)
   async def root(request: Request):
       return templates.TemplateResponse("index.html", {"request": request})
   ```

4. The entire `_HTML = r"""..."""` string literal (4,018 lines) was deleted.

### What `ui/templates/index.html` contains

The template is a direct reconstruction of the original HTML:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>MCP Factory</title>
    <link rel="stylesheet" href="/static/app.css" />
    <script src="https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js"></script>
  </head>
  <body>
    [830 lines of body markup, extracted verbatim]
  </body>
  <script src="/static/app.js"></script>
</html>
```

The `<link rel="stylesheet">` replaces the inline `<style>` block.
The `<script src="/static/app.js">` replaces the inline `<script>` block.
**No HTML structure, class names, IDs, or event handlers were changed.**

### What the static files contain

- **`ui/static/app.css`**: the verbatim content of the original `<style>` block
  (CSS variables, component styles, animations, responsive breakpoints). No
  modifications.
- **`ui/static/app.js`**: the verbatim content of the original `<script>` block
  (SPA state management, API polling, WebSocket-style SSE consumption, tool
  rendering, chat UI). No modifications. The `<script>` and `</script>` wrapper
  tags were stripped; pure JS only.

### Known failure modes for Item 3

**If the UI shows unstyled HTML or missing functionality:**

- Check that `ui/static/` exists and is readable by the uvicorn process.
- Check that `jinja2` is installed in the UI venv (`pip install jinja2`).
- Check that the `/static` mount is registered before the `@app.middleware("http")`
  decorator fires. The mount is at lines 123–125 of `ui/main.py`; the middleware
  is at line 127+. FastAPI evaluates mounts before route middleware in practice,
  but if the key guard returns 401 for `/static/app.css`, the browser will get
  unstyled output. The existing `_api_key_guard` middleware only checks
  `/health`, `/favicon.ico`, and `/copilot` by path; **static file requests are
  not explicitly whitelisted**. If `UI_API_KEY` is set, requests to
  `/static/app.css` and `/static/app.js` will be intercepted by the guard before
  they reach the static file handler because FastAPI evaluates middleware before
  mounts for non-`Mount` routes. To fix: add `"/static"` path prefix check to
  `_api_key_guard` in `ui/main.py`.

**If Jinja2 raises `TemplateNotFound: index.html`:**

- Confirm `ui/templates/index.html` exists.
- Confirm the process working directory is not changing `Path(__file__)` resolution.
  `_UI_DIR = Path(__file__).resolve().parent` should give the absolute path to
  the `ui/` directory regardless of CWD, but verify with a quick print of `_UI_DIR`
  if needed.

**If the login page (the `login_html` string inside `_api_key_guard`) looks broken:**

- That string is **not** the extracted `_HTML` blob. It is a separate small
  inline HTML string defined inside the middleware function body (around line 146
  of the new `ui/main.py`). It was not touched. Do not confuse the two.

### Rollback

To revert Item 3 without git:

1. Restore the `_HTML = r"""..."""` blob (can be reconstructed by concatenating
   the head from template lines 1–9, `<style>` + app.css content + `</style>`,
   CDN script line, body from template lines 11–841, `<script>` + app.js content
   - `</script></body></html>"""`).
2. Change the `@app.get("/")` route back to `return HTMLResponse(_HTML)`.
3. Remove the `app.mount` and `templates = ...` lines.
4. Remove the `StaticFiles` and `Jinja2Templates` imports.

## Item 4 — Extract body parsers and health probes from `api/routes/main.py` {#item-4}

- `api/routes/main.py` — removed ~500 lines of helper functions; added imports
- `api/routes/body_parsers.py` — **new file**: 255 lines
- `api/routes/health_probes.py` — **new file**: 335 lines

### Why

`api/routes/main.py` had grown to 2,041 lines. Approximately 25% of that was
helper code that had nothing to do with HTTP routing:

- **Body parsers** (`_as_bool`, `_as_int`, `_as_float`, all the `_normalize_*`
  and `_extract_*` functions): pure Python with no FastAPI imports, no I/O. They
  belonged in a utility module, not in the router file.

  `_recent_job_entries`, `_probe_bridge_status`, `_probe_model_status`,
  `_probe_storage_status`, `_probe_queue_status`, `_select_active_job`,
  `_compute_lane_validity`, `_refresh_campaign_poll_state`): service-health I/O
  that is logically a separate concern from the endpoint dispatcher.

The separation makes the router easier to read, makes the helpers independently
testable, and reduces merge conflict surface.

### Known failure modes for Item 4

**`ImportError: cannot import name '_LAB_PROBE_LOCK' from 'api.routes.health_probes'`**
— means `health_probes.py` either doesn't exist at deploy time or was not
included in the container image build. Check that `api/routes/health_probes.py`
is tracked in git / included in `COPY` in the Dockerfile.

**Circular import** — `health_probes.py` imports from `api.infra.storage` which
is also imported by `routes/main.py`. This is not a circular dependency because
neither module imports from `api.routes`. If a circular import error appears,
check whether any new import was added to `health_probes.py` that pulls in
something that eventually imports `api.routes.main`.

**TTL cache scope confusion** — if two test files both import `_LAB_PROBE_CACHE`
from different paths (e.g. one from `api.routes.health_probes` and another
importing it indirectly via `api.routes.main`), they will share the same object
in a single Python process, which is the intended behaviour. If a test patches
`api.routes.main._LAB_PROBE_CACHE`, it will no longer work; patch
`api.routes.health_probes._LAB_PROBE_CACHE` instead.

**`_startup_probe` dead code** — there are two startup probe functions in
`routes/main.py`:

- `_startup_probe()` — defined but **never called**. Registered as dead code in
  the original review. It was intentionally left in place during this refactor
  (not our change to remove) to avoid a larger scope change.
- `_local_startup_probe()` — the one that is actually called by `@app.on_event("startup")`.

Do not be confused by both functions existing. If you remove `_startup_probe`,
nothing will break.

### Rollback

Copy the function bodies from `body_parsers.py` and `health_probes.py` back into
`routes/main.py` (before the `# ── FastAPI app` section for body parsers, and
between the `@app.get("/health")` and `@app.get("/api/lab/status")` definitions
for health probes). Then remove the two `from api.routes.body_parsers import`
and `from api.routes.health_probes import` blocks, and restore the two pipeline
imports that were removed:

```python

```

## Known Risks {#known-risks}

### High priority

1. **`_api_key_guard` does not whitelist `/static/*` paths.** If `UI_API_KEY` is
   set in the environment, requests for `app.css` and `app.js` will hit the
   middleware before reaching the static file mount. FastAPI's `StaticFiles` mount
   is not a standard route and may or may not be intercepted depending on FastAPI
   version. The fix is to add a path-prefix check in `ui/main.py`:

   ```python
   if request.url.path.startswith("/static"):
       return await call_next(request)
   ```

   This was not added in this refactor to avoid modifying middleware logic beyond
   the stated scope.

2. **`jinja2` and `aiofiles` are listed in `ui/requirements.txt` but may not be
   installed in existing venvs.** Run `pip install jinja2 aiofiles` in the UI
   venv before restarting the service. If you see `ModuleNotFoundError: No module
named 'jinja2'`, this is the cause.

### Medium priority

3. **Container image cache.** If the UI is deployed via Docker and the image is
   cached from before this refactor, the `ui/static/` and `ui/templates/`
   directories will not exist in the container. Rebuild the image from scratch
   (`docker build --no-cache`).

4. **The mermaid CDN script.** The original HTML loaded mermaid from
   `https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js`. This is
   preserved verbatim in `ui/templates/index.html`. If the network is air-gapped
   or the CDN is unavailable, the pipeline diagram will fail to render. This was
   a pre-existing risk, not introduced here.

5. **`_append_executor_trace` is still present and exported** from `storage.py`
   even though the 2026-04-04 refactor notes mentioned it was part of the
   overlap-evidence contamination investigation. The function now delegates to
   `_append_json_list` and its public signature is unchanged. If a bug is found
   in `executor_trace.json` blob contents, check both the call site and the
   `_append_json_list` generic path.

### Low priority

6. **Source map / dev-tools experience.** `app.js` is now served as a flat file.
   If a browser dev-tools breakpoint was set by line number inside the old Python
   string, the line numbers will differ. The JS content itself is identical.

7. **Jinja2 auto-escaping.** `Jinja2Templates` in FastAPI defaults to
   auto-escaping HTML entities in template variables. The current template passes
   only `{"request": request}` with no user-supplied variables, so this is a
   non-issue for the current template. If template variables are added in future,
   be aware of auto-escaping behaviour for raw HTML values.
