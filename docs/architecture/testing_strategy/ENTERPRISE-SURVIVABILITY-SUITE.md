# Enterprise Survivability Suite

## Purpose

This suite family answers a different question than stage breakpoint tests:

`When the pipeline cannot solve every target, can it still finish with useful, attributable, non-misleading packets?`

Breakpoint tiers prove local stage, seam, coordinator, or bottom-up obligations. Enterprise survivability tiers prove end-to-end operational diagnosability under partial failure. Hard-family measurement-fabric rows live in [`HARD-FAMILY-MEASUREMENT-FABRIC.md`](HARD-FAMILY-MEASUREMENT-FABRIC.md) and own the lower-level runner/API/discovery/bridge/analyzer network that creates comparable or non-comparable packets. Hard-family traffic-light admission lives in [`HARD-FAMILY-MEASUREMENT-CONTROL-PLANE.md`](HARD-FAMILY-MEASUREMENT-CONTROL-PLANE.md).

Compiled-suite green labels live in
[`COMPILED-SUITE-GREEN-CONTRACT.md`](COMPILED-SUITE-GREEN-CONTRACT.md).
Enterprise survivability green is diagnosability green. It is not product-green
unless a separate compiled enterprise product route proves Ghidra-backed
discovery and decision-bearing semantic/product evidence.

## Benchmark Question

Can a hard-shaped run preserve comparable evidence, non-comparable failures, skipped dependency boundaries, critical warnings, and final suite packets without claiming semantic proof it did not earn?

## Lane Identity Comparability Guard

Hard-family semantic evidence is comparable only when the runner, API, and bridge
prove they belong to the same local code context. For v1 hard-family local
comparability, exact runner/API/bridge git SHA equality is required. Dirty state
is recorded and operator-visible, but SHA mismatch blocks comparability.

Managed local API and bridge processes are stale when their `/identity.git_sha`
differs from the current repo HEAD. Managed stale processes should be restarted.
Unmanaged or restart-suppressed processes must remain non-comparable with an
explicit freshness verdict such as `restart_blocked_unmanaged_owner` or
`restart_suppressed_git_sha_mismatch`.

This guard can prove lane trust only. It cannot make `hard01` semantically pass,
repair `reservation_stage` discovery, or promote any S-00 through S-07 breakpoint
row.

## Analyze/Discovery Authority Row

Hard-family analyze/discovery authority is now owned by
[`HARD-FAMILY-MEASUREMENT-FABRIC.md`](HARD-FAMILY-MEASUREMENT-FABRIC.md). This
suite records the dependency because survivability cannot advance to Tier 4
while the measurement fabric cannot route `reservation_stage` through enforced
bridge admission. Bridge-health input now prevents unproven or recently stalled
bridge-stream health from silently remaining comparable green, and Tier 2
control-plane enforcement forces yellow targets to stay diagnostic-only while
blocking red/quarantined targets before analyzer scheduling.

The row remains a measurement row, not a hard01 pass claim. It asks whether a
hard-shaped binary can either produce trusted discovery output or fail with a
precise non-comparable analyzer packet.

| Scope | Breakpoint family | Current tier | Target tier | First proof case | Claim ceiling |
| --- | --- | --- | --- | --- | --- |
| hard-family analyze/discovery | analyze/discovery authority for hard-shaped binaries | Tier 2 classifier evidence exists | Tier 3 mixed hard-shaped binaries | `reservation_stage` | analyzer/discovery classification only; no hard01 semantic maturity |

The required analyzer packet preserves status, progress, error text, last
observation, checked output paths, found output files, timeout or stall
classification, `safe_to_compare=false`, and
`discovery_output_present=false` when only status files exist. A non-comparable
analyzer packet is baseline data only; it cannot satisfy compiled ingest proof
or semantic checkpoint alignment.

Measurement-fabric ownership keeps this taxonomy out of S-00 through S-07 stage
breakpoint tiers. A lane, discovery, bridge, or Ghidra failure can block hard01
comparison without weakening a stage row unless a later semantic packet routes
there explicitly.

## Object-Bound Corrective Authority

Enterprise corrective actions must prove what object was corrected, rejected,
revoked, quarantined, rolled back, or denied. A status such as success is not
enough when the product claim depends on invalidating a specific replay branch,
revoking a specific stale entitlement, rejecting a specific duplicate
settlement, or quarantining a specific unsafe path.

This is the survivability-specific form of the Decision-Bearing Provenance
Principle in `AGENTS.md`: the run must prove the selected object, the decision
basis, the downstream corrective action, and the final authority binding.

For the current Spectrum hard-family pressure, `SP_InvalidateUntrustedBranch`
is the first proof surface. The survivability family is broader than Hard01:
final authority must show distinct trusted and rejected objects, prove the
corrective invocation used that pair, and bind the returned token or audit
evidence to the rejected object. If those bindings are missing, the canonical
blocker is `object_bound_corrective_authority_missing` or the sharper
`branch_invalidation_token_not_tied_to_rejected`, not a generic `pipeline`
failure.

Hard03 extends the same family into unsafe-path denial and quarantine. Its
authored pressure is not another branch-invalidation variant: it asks whether a
specific unsupported target can be denied, quarantined, and audit-recorded with
the target identity preserved across the quarantine token and final audit token.
The first Hard03 standing run is baseline discovery only, not product-green or
Gate V1 promotion evidence.

## Questions This Suite Can Answer

- Did the pipeline finish with a reviewable packet when some targets failed?
- Did non-comparable targets remain separate from semantic proof?
- Did dependency-invalid targets get skipped rather than run blindly?
- Did warnings survive into the final operator-facing packet?

## Questions This Suite Cannot Answer

- It cannot prove a stage breakpoint row is Tier 2.
- It cannot prove hard01/hard02 semantic maturity.
- It cannot prove product behavior correctness.
- It cannot replace compiled runtime evidence where runtime behavior is the claim.
